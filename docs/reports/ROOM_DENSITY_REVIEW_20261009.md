# 방 크기·지도 밀도 검토

Status: REVIEWED / 생성 규칙 변경은 PROPOSED. 운영 변경 없음.

## 사용자 요청과 구현 범위

2026-10-09 사용자는 현대 2D RPG 그래픽·UI 구현을 승인한 뒤, 기존 맵의 불필요하게 넓은 방을 줄이는 방안도 검토하도록 요청했다. 이 문서는 그 추가 검토 결과다. 기존 시각 개편 승인을 던전 생성·밸런스 변경 승인으로 확대하지 않는다.

## 현재 원인

- `src/dungeon/balance.ts`: 층 48×34, 일반 방 4~9×4~7칸, 5~9개 방, 방 간 padding 2.
- `web/src/map.ts`: 기본 반경 5, 즉 플레이어 중심 11×11칸 표시. 넓게 보기 반경 7은 15×15칸이다.
- 방 크기는 화면의 캐릭터 크기를 직접 결정하지 않는다. 같은 캔버스와 표시 범위에서 방만 작게 만들면 타일 크기는 그대로다.
- 현재 큰 방은 가장자리에서 플레이어 중심 카메라 밖으로 이어질 수 있다. 표시 범위를 좁히려면 공개된 방 안에서 카메라 프레이밍도 함께 검토해야 한다.

## 격리 생성 비교

재현: `npm run build` 후 `node scripts/review-room-density.mjs`.
실험은 빌드 결과의 임시 복사본만 변경한다. 실제 소스의 생성 상수와 저장 데이터를 수정하지 않는다.
9개 캠페인의 123개 층 계획을 순환하며 프로필당 동일한 1,000개 seed/spec를 사용했다. 후보 상한은 보스방을 포함한 모든 일반 방에 적용했다. 방 역할별 예외를 두는 최종안은 아직 검사하지 않았다.

*최단거리는 상하좌우 BFS이며 문·비밀 통로를 열 수 있는 지형으로 취급했다. 실제 8방향 이동, 수색, 전투, 방문 순서가 포함된 플레이 시간이나 행동 수가 아니다.

모든 프로필에서 동일 seed/spec의 반복 생성 일치와 필수 지점 연결성 PASS. 빌드 PASS. 조작감, 모바일 화면, 난이도, 군량 소모, 기존 저장 복원과 캠페인별 실제 플레이는 NOT_RUN.

## 추천 Delta

1. 일반 방은 4~6×4~6칸을 기본 후보로 삼는다. 대형 방은 보스·특수 기믹처럼 이유가 있는 경우에 제한한다. 대형 방 예외의 수치와 배치 가능성은 별도 구현 검증이 필요하다.
2. 기본 표시 범위는 11×11→9×9칸 후보로 함께 변경한다. 같은 캔버스 크기라면 타일·유닛 표시 폭이 약 22% 커진다. 이는 산술 비교이며 실제 렌더링 결과는 아직 검증하지 않았다. 넓게 보기는 유지한다.
3. 공개된 방의 경계·출구가 읽히도록 카메라 프레이밍을 조정하되 미탐험 정보는 노출하지 않는다. 지도 터치 좌표와 카메라 이동의 일치를 검사한다.
4. 층 40×28은 이동량 개선 후보로 유지한다. 방만 줄이면 복도는 약 8% 늘었다. 층도 줄이면 시작→계단의 위 최단거리 지표는 약 16% 줄었다. 적 밀도·군량·탐지/기습·수색 위험이 달라지므로 시각 수정으로 취급하지 않는다.

첫 적용 후보는 방 축소와 화면 확대의 조합이다. 층 전체 축소는 실제 플레이 비교를 거친 후 결정한다. 생성 검사 통과만으로 밸런스 유지나 UX 개선을 확정하지 않는다.

## 저장 호환성

`web/src/main.ts`의 save v1은 지도 스냅샷이 아닌 `options + command log`다. 이어하기는 같은 seed로 지도를 재생성하고 명령을 재실행한다. 생성 상수만 바꾸면 기존 기록이 다른 지도로 재생되어 위치·물품·전투 결과가 달라질 수 있다.

생성 규칙을 적용할 경우 기존 기록에는 legacy 생성기를 지정하고 새 원정에는 버전이 있는 compact 생성기를 사용해야 한다. 버전이 없는 기존 기록은 legacy로 해석하며, 복원 중 새 규칙으로 자동 전환하거나 세이브를 삭제하지 않는다. 실제 구현 전 RunOptions/save 버전과 모든 층 생성의 전달 경로를 명세·검증해야 한다.
